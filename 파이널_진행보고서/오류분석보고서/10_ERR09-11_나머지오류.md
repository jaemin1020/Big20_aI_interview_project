# ERR-09: 인터뷰 시나리오 파일 경로 하드코딩 (Docker/Windows 환경 불일치)

- **오류 코드**: ERR-09  
- **카테고리**: 비즈니스 로직 / 환경 설정  
- **심각도**: 🟠 MEDIUM  
- **상태**: ✅ 해결 완료  
- **관련 파일**: `ai-worker/tasks/question_generator.py`, `ai-worker/main.py`

---

## 3.2.1 문제 정의

`ai-worker`가 `backend-core`의 인터뷰 시나리오 설정 파일을 불러올 때 Linux/Docker 전용 절대 경로(`/backend-core/...`)로 하드코딩되어 있어, Windows 로컬 개발 환경에서 `ImportError`가 발생하였습니다.

- **현상**: 로컬 실행 시 `ModuleNotFoundError: No module named 'config.interview_scenario'` 발생
- **재현 조건**: Windows에서 직접 `ai-worker` 실행 시 발생 (Docker에서는 정상)

---

## 3.2.2 문제 영향 분석

- **개발 편의성 영향**: 로컬에서 테스트/디버깅 불가
- **기능 영향**: ImportError 발생 시 fallback으로 표준 시나리오만 로드되어 직무 전환 시나리오가 무조건 미작동

---

## 3.2.3 문제 파악 과정

```python
# [문제 코드] ai-worker/tasks/question_generator.py
from config.interview_scenario import get_next_stage as get_next_stage_normal
from config.interview_scenario_transition import get_next_stage as get_next_stage_transition
```

`sys.path`에 `/app`(Docker 경로)만 추가되어 있고, Windows 로컬 경로 (`C:\big20\...\backend-core\config`)가 누락됨.

```python
# [문제 코드] ai-worker/main.py L8
app_root = "/app" if os.path.exists("/app") else os.path.dirname(os.path.abspath(__file__))
backend_root = os.path.abspath(os.path.join(app_root, "..", "backend-core"))
# → Windows 로컬에서 app_root가 ai-worker 디렉토리가 되지만,
#   backend-core의 config 폴더까지의 경로가 sys.path에 추가되지 않음
```

---

## 3.2.4 해결 접근 전략

- Docker 환경(`/app`)과 Windows 로컬 환경(`C:\big20\...`) 모두를 자동 감지하는 경로 탐색 로직 적용
- `sys.path`에 `backend-core` 루트 경로를 명시적으로 추가

---

## 3.2.5 해결 도출 및 실행

```python
# [수정 후] ai-worker/main.py L6-21
app_root = "/app" if os.path.exists("/app") else os.path.dirname(os.path.abspath(__file__))
backend_root = os.path.abspath(os.path.join(app_root, "..", "backend-core"))

# 우선 다 지우고 새로 추가 (순서 보장)
for p in [app_root, backend_root]:
    while p in sys.path:
        sys.path.remove(p)

sys.path.insert(0, backend_root)  # backend가 2순위
sys.path.insert(0, app_root)      # app_root가 최종 1순위

# config 폴더 위치를 명시적으로 보장
config_parent = os.path.dirname(os.path.abspath(__file__))
if config_parent not in sys.path:
    sys.path.insert(0, config_parent)
```

```python
# [수정 후] ai-worker/tasks/question_generator.py L17-18
if "/app" not in sys.path:
    sys.path.insert(0, "/app")
# → Docker: /app에서 config 임포트
# → Windows: main.py에서 설정된 backend_root 경로로 임포트
```

---

## 3.2.6 해결 결과

- **Before**: Windows 로컬 실행 시 `ImportError` 발생, 시나리오 파일 로드 불가
- **After**: Docker/Windows 환경 자동 감지로 두 환경 모두에서 정상 임포트
- **교훈**: 멀티 환경(Docker, Windows 로컬, CI/CD)에서 실행되는 코드는 절대 경로를 하드코딩하지 말고, 실행 환경을 자동 감지하는 동적 경로 설정을 사용해야 함

# ERR-10: analyze_answer 태스크 106초 처리 지연

- **오류 코드**: ERR-10  
- **카테고리**: 성능 / 지연  
- **심각도**: 🟡 LOW  
- **상태**: 🔄 부분 해결  
- **관련 파일**: `ai-worker/tasks/evaluator.py`

---

## 3.2.1 문제 정의

면접 중 지원자 답변 실시간 평가(`analyze_answer`) 태스크가 평균 106초 소요되는 성능 문제가 발생하였습니다.

- **현상**: 답변 제출 후 다음 질문까지 106초 이상 대기 발생
- **발생 위치**: `evaluator.py` → `_analyze_answer_logic()` 함수

---

## 3.2.2 문제 영향 분석

- **사용자 경험 영향**: 면접이 부자연스럽게 끊기는 느낌 (실시간 면접이 아닌 턴 기반처럼 보임)
- **시스템 영향**: GPU 워커가 평가 태스크에 묶여 질문 생성 태스크 처리 지연

---

## 3.2.3 문제 파악 과정

1. **EXAONE JSON 파싱 부담**: `analyze_answer`는 LLM에게 JSON 형식 출력을 요구하는데, EXAONE이 JSON을 안정적으로 생성하지 못해 파싱 재시도가 발생
2. **루브릭 로딩 오버헤드**: 매 평가마다 `create_evaluation_rubric()`을 호출하여 전체 루브릭을 로드
3. **실시간 처리 필요성 불명확**: `analyze_answer`는 면접 중 실시간이 아닌 면접 종료 후 일괄 처리해도 무방한 태스크임

---

## 3.2.4 해결 접근 전략 (부분 해결)

- 면접 중 `analyze_answer`를 즉시 실행하지 않고, 면접 종료 후 `generate_final_report` 파이프라인에서 일괄 병렬 처리
- 루브릭을 캐싱하여 매 호출마다 재로딩하지 않도록 개선

---

## 3.2.5 해결 도출 및 실행

```python
# [수정 후] evaluator.py L251-274
# 면접 종료 후 일괄 병렬 처리 (group + chain)
def generate_final_report(interview_id: int):
    transcripts = get_user_answers(interview_id)
    subtasks = []
    for t in transcripts:
        if t.total_score is None or t.total_score == 0:
            subtasks.append(
                analyze_answer.s(transcript_id=t.id, ...)
            )
    
    if subtasks:
        logger.info(f"⛓️  Parallelizing {len(subtasks)} answer evaluations...")
        workflow = chain(group(subtasks), finalize_report_task.s(interview_id))
        return workflow.apply_async()
```

---

## 3.2.6 해결 결과

- **Before**: 면접 중 매 답변마다 106초 평가 대기
- **After**: 면접 중에는 평가 스킵 → 종료 후 Celery `group`으로 병렬 일괄 평가
- **미해결**: EXAONE 자체의 JSON 생성 불안정성은 현재 모델 한계로 완전 해결 미완료

# ERR-11: LangSmith 트레이싱 미작동 (커스텀 LLM)

- **오류 코드**: ERR-11  
- **카테고리**: LLM / 운영 모니터링  
- **심각도**: 🟡 LOW  
- **상태**: 🔄 부분 해결  
- **관련 파일**: `ai-worker/utils/exaone_llm.py`

---

## 3.2.1 문제 정의

LangSmith 대시보드에서 EXAONE LLM 호출 트레이스가 기록되지 않는 문제가 발생하였습니다.

- **현상**: LangSmith 환경변수 설정 후에도 EXAONE 추론 로그가 LangSmith에 미전송
- **원인**: `ExaoneLLM`이 LangChain의 표준 `BaseLLM`을 완전히 상속하지 않은 커스텀 구현체라 LangSmith 훅(Callback)이 자동으로 연결되지 않음

---

## 3.2.2 문제 영향 분석

- **운영 모니터링 영향**: 프롬프트 디버깅, 토큰 사용량 추적 불가
- **개발 생산성 영향**: A/B 프롬프트 테스트 결과를 LangSmith UI로 확인 불가

---

## 3.2.3 ~ 3.2.5 분석 및 해결

**원인**: `ExaoneLLM`이 `llama_cpp.Llama`를 직접 래핑한 커스텀 클래스로, LangChain의 `CallbackManager` 훅이 연결되지 않음.

**부분 해결**: LangChain의 `BaseLLM._call()` 메서드를 `super()`를 통해 올바르게 연결하고, `LANGCHAIN_TRACING_V2=true` 환경변수를 docker-compose에 명시.

**미해결**: `llama-cpp-python` 기반 커스텀 LLM의 LangSmith 완전 통합은 공식적으로 지원하지 않아 수동 콜백 주입 방식으로만 부분 기록 가능.

---

## 3.2.6 해결 결과

- **Before**: LangSmith에 EXAONE 트레이스 전혀 없음
- **After**: 일부 LangChain 체인(PromptTemplate → LLM → Parser) 단위 트레이스 기록 가능
- **미해결**: `llm.invoke()` 직접 호출 구간은 여전히 트레이스 미기록
- **교훈**: 커스텀 LLM 구현 시 LangChain 표준 인터페이스(`BaseLLM` 상속, `_call()` 구현)를 완전히 준수해야 LangSmith 등 LangChain 생태계 도구와 완전 호환됨
