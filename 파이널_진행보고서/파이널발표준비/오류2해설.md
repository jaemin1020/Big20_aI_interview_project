# [오류 사례 2] Celery 태스크 명칭 불일치 및 큐 라우팅 해설

이 문서는 분산 시스템에서 서버(Backend)와 일꾼(Worker) 간의 대화가 어긋나는 **'태스크 네이밍 불일치'** 문제를 해결하고, 효율적인 자원 배분을 위해 **'CPU/GPU 전용 큐 라우팅'**을 구축한 과정을 상세히 설명합니다.

---

## 1. 문제 상황 (Problem Definition)
*   **현상:** 이력서 업로드 후 파싱이나 면접 질문 생성이 실행되지 않고 무한 대기 상태에 빠짐.
*   **로그:** `[ERROR] Received unregistered task "tasks.question_generation.*"`
*   **원인:** Git 브랜치 병합 과정에서 파일명이나 함수명이 리팩토링되었으나, Celery가 서로를 식별하는 **'태스크 이름(String)'**이 동기화되지 않아 발생한 통신 오류.

---

## 2. 해결 전략: "표준 규격 봉투와 전용 우편함" 비유

### 🔵 태스크 네이밍 고정 (표준 규격 봉투)
Celery 시스템에서는 함수 이름보다 **`name="..."`**으로 지정된 문자열이 훨씬 중요합니다.
> **비유:** 편지를 보낼 때 봉투에 '홍길동에게'라고 적는 대신, 우체국이 정한 **'표준 코드(tasks.question_generation.XXX)'**를 적기로 약속한 것입니다.
*   함수 이름이 `generate_next_question`이든 `generate_question_task`이든 상관없이, 봉투에 적힌 **'표준 코드'**만 보고 정확히 배달할 수 있게 설계했습니다.

#### ❓ 왜 Git은 이런 걸 자동으로 통일해주지 못하나요? (수동 해결의 필연성)
많은 분들이 "Git이 똑똑하면 알아서 이름을 통일해줘야 하는 것 아니냐"고 질문합니다. 하지만 여기에는 기술적인 이유가 있습니다.
1.  **Git은 텍스트 도구입니다:** Git은 줄(Line) 단위로 글자가 바뀐 것은 알지만, 그 글자가 어떤 **'의도'**를 가졌는지는 모릅니다. A개발자는 `create`로, B개발자는 `generate`로 바꿨을 때 누구의 선택이 옳은지 컴퓨터는 판단할 수 없습니다.
2.  **프랑켄슈타인 코드 방지:** 만약 컴퓨터가 멋대로 두 코드를 섞어버리면, 문법이 꼬여서 서버가 아예 켜지지 않는 치명적인 에러가 날 수 있습니다.
3.  **우리의 해결책 (Naming Standard):** 결국 사람이 매번 싸우지 않도록, 우리는 **"파일 이름이 어떻게 변하든 Celery 태스크 이름만은 표준 규격(tasks.XXX.YYY)을 따르자"**는 절대 규칙을 코드에 박아버린 것입니다. (이것이 진정한 의미의 자동 방어입니다.)

### 🔴 큐 라우팅 (전용 우편함 분리)
모든 편지를 한 바구니에 담지 않고, 성격에 따라 **우편함을 두 개(CPU/GPU)**로 분리했습니다.
> **비유:** '가벼운 엽서(CPU 작업: PDF 파싱)'와 '무거운 택배(GPU 작업: AI 질문 생성)'를 분리하여, 택배가 밀려도 엽서는 바로 배달될 수 있게 만든 것입니다.

## 3. 실제 코드 적용 분석

### ① 태스크 이름 명시적 고정 (name 속성 활용)
파일명이나 함수명이 바뀌어도 통신이 끊기지 않도록 고정된 이름을 부여했습니다.

```python
# [위치] ai-worker/tasks/question_generator.py (Line 86)
# 함수명은 generate_next_question_task이지만, Celery는 'tasks.question_generation.*'으로 소통함
@shared_task(bind=True, name="tasks.question_generation.generate_next_question")
def generate_next_question_task(self, interview_id: int):
    ...
```

```python
# [위치] ai-worker/tasks/resume_parser.py (Line 30)
# 이력서 파이프라인 전용 이름을 부여하여 관리 효율성 확보
@shared_task(bind=True, name="tasks.resume_pipeline.parse_pdf", queue='cpu_queue')
def parse_resume_pdf(self, resume_id: int, file_path: str):
    ...
```

### ② 정교한 큐 라우팅 규칙 정의 (`main.py`)
태스크 이름에 따라 어떤 전용 일꾼(CPU/GPU)이 처리할지 규칙을 세웠습니다.

```python
# [위치] ai-worker/main.py (Line 64-73)
app.conf.update(
    task_default_queue='cpu_queue', # 기본값은 CPU 처리
    task_routes={
        # 1. AI 질문 생성 및 모델 로딩은 무조건 GPU 전용 칸(gpu_queue)으로!
        'tasks.question_generation.*': {'queue': 'gpu_queue'},
        
        # 2. 이력서 텍스트 수치화(Embedding)도 GPU로!
        'tasks.resume_pipeline.generate_embeddings': {'queue': 'gpu_queue'},
        
        # 3. 나머지는 기본값(cpu_queue)에 따라 자동으로 CPU 일꾼이 처리
    }
)
```

## 4. 해결 결과 및 기술적 가치

1.  **통신 오류 완전 소멸:** 태스크 이름을 고정(Hard-coding)함으로써 리팩토링이나 코드 병합 시에도 "모르는 태스크" 에러가 발생하지 않습니다.
2.  **자원 최적화 설계:** 
    *   **CPU 워커:** 가벼운 PDF 파싱, 데이터 전처리에 집중 (병렬 처리 지원)
    *   **GPU 워커:** 무거운 AI 연산에만 전념 (순차 처리 지원)
3.  **시스템 확장성:** 특정 작업이 밀려도 다른 큐는 영향을 받지 않으므로, 부하 발생 시 특정 일꾼(Worker)만 개별적으로 늘릴 수 있는 **'유연한 확장성'**을 확보했습니다.

## 🎯 총정리: 발표용 핵심 멘트

> "저희는 분산 서버 환경에서 발생할 수 있는 대화의 어긋남을 막기 위해 **'태스크 네이밍 표준화'**를 도입했습니다. 또한, 단순한 작업은 CPU로, 무거운 AI 연산은 GPU로 보내는 **'지능형 큐 라우팅'** 설계를 통해 시스템의 처리 효율과 코드의 유지보수성을 동시에 잡았습니다."
