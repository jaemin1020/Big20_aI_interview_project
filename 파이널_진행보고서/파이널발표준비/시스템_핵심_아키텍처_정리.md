# 시스템 핵심 아키텍처 및 기술적 특징 정리

이 문서는 AI 모의면접 시스템의 고가용성 확보와 시스템 부하 분산을 위해 적용된 핵심 기술적 장치(폴백 설계, 비동기 인프라, API 서버 구조, 병렬 처리)를 정리한 리포트입니다.

---

## 1. 폴백(Fallback) 설계 기반의 고가용성 서비스 아키텍처

### 1.1 개요
AI 모델(LLM, STT 등)의 장애나 일시적인 오류가 발생하더라도 면접 서비스 자체가 중단되지 않도록 하는 **'장애 허용(Fault Tolerance)'** 설계입니다.

### 1.2 실제 코드 적용 위치
1.  **질문 생성 핵심 폴백 (`ai-worker/tasks/question_generator.py`)**
    *   **재시도(Retry):** LLM 생성 실패 시 3초 간격으로 최대 3회 자동 재시도.
    *   **스테이지별 폴백 사전:** 3회 재시도 실패 시, 현재 면접 스테이지에 맞는 '사전 정의된 기본 질문'을 자동으로 추출하여 면접 중단 방지.
2.  **시나리오 로딩/이력서 구조화 폴백**
    *   설정 파일 누락이나 LLM 파싱 실패 시에도 빈 구조를 반환하여 전체 시스템의 가동 중단을 원천 차단.

---

## 2. Celery Worker 기반 비동기 인프라

### 2.1 핵심 아키텍처 (Fire-and-Forget)
API 서버가 모든 일을 처리하지 않고, 무거운 AI 연산을 백그라운드 일꾼(Worker)에게 맡기는 구조입니다. 사용자에게는 즉시 응답을 주고, 실제 연산은 뒤에서 이루어집니다.

### 2.2 리소스 최적화: 큐(Queue) 라우팅 분리
*   **`gpu_queue`**: LLM 질문 생성 전용. (메모리 보호를 위해 순차 처리)
*   **`cpu_queue`**: STT, TTS, PDF 파싱 전용. (성능 극대화를 위해 병렬 처리)

---

## 3. 병렬 처리 (Parallel Processing) 전략

### 3.1 워커 내부의 멀티태스킹 (`concurrency=4`)
CPU 워커는 내부적으로 4개의 스레드(Thread)를 가동하여 **STT, TTS, PDF 파싱, 청킹** 등의 작업을 동시에 병렬로 처리합니다.

### 3.2 설정 근거: 왜 '--concurrency=4' 인가? (리소스 격리 전략)
이 수치는 호스트 PC의 전체 자원(예: 6 Core, 32GB RAM)을 모두 쓰는 것이 아니라, 다음의 **전략적 리소스 배분**에 따라 설계되었습니다.

1.  **호스트 OS 및 타 서비스 보호 (Resource Buffering):** 시스템 전체 자원 중 일부(2 Core, 16GB RAM)를 의도적으로 제외했습니다. 이는 Windows OS, VS Code, 브라우저 등 호스트 환경의 안정성을 유지하고 시스템 멈춤(Freezing)을 방지하기 위한 '숨 쉴 공간'입니다.
2.  **멀티 컨테이너 아키텍처 대응:** 프로젝트는 DB, Redis, Backend, Media Server 등 총 7개의 컨테이너가 동시에 가동됩니다. 특히 실시간 처리가 중요한 Media Server와 Backend의 연산 자원을 보장하기 위해 CPU 워커의 점유율을 적정 수준(4코어)으로 제한했습니다.
3.  **CPU 코어 매칭 (Core Affinity):** 할당된 4.0 Core 내에서 작업 개수를 1:1로 맞춤으로써 불필요한 문맥 전환(Context Switching)을 최소화하고 STT/TTS의 고부하 연산 속도를 100% 활용합니다.
4.  **클라우드 표준 인스턴스 설계:** 추후 서버 확장(Scale-out) 시, 클라우드 환경의 표준 규격(예: c5.xlarge급)에 맞춰 서버를 동일한 단위로 복제하여 늘릴 수 있도록 규격화된 설계를 적용한 것입니다.

## 4. API 서버의 정의 및 프로젝트 내 작용

API 서버는 시스템의 **'뇌'이자 '컨트롤 타워'**로서 식당의 **홀 매니저(웨이터)**와 같은 역할을 합니다.

### 4.1 홀 매니저 비유를 통한 이해
*   **손님 (Frontend):** "내 이력서 보여줘!", "나 답변했어!"라고 요청.
*   **API 서버 (Backend/FastAPI):** 요청을 확인(로그인 체크 등)하고 명령을 하달.
*   **주방 (AI-Worker/DB):** 실제 고난도 연산을 수행하고 결과를 창고에 기록.

### 4.2 컨트롤 타워로서의 실제 코드 작용
`transcripts.py`에서 보듯, API 서버는 답변을 받자마자 DB에 일단 기록한 후, Celery를 통해 **"다음 질문 생성해!"**라고 비동기 명령을 던짐으로써 자신의 스레드를 차단(Blocking)하지 않고 계속해서 수많은 사용자의 요청을 실시간으로 받아낼 수 있습니다.
