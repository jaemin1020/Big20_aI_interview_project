# [오류 사례 6] API 통신 및 프론트엔드 타이밍 오류 해설 (복구 및 상세 보강본)

이 문서는 비동기 분산 환경에서 발생하는 **경합 조건(Race Condition)**과 **데이터 정렬** 문제를 해결하여 면접의 논리적 흐름과 리포트의 정합성을 확보한 과정을 상세히 설명합니다.

---

## 1. 문제 상황 (Problem Definition)
*   **현상:** 지원자가 답변을 마치기도 전에 다음 질문이 조기 생성되거나, DB 조회 시 면접 기록의 순서가 뒤섞여 리포트 질문/답변 순서가 꼬이는 현상 발생. 
*   **원인:** 비동기 작업의 상태값(Status) 동기화 누락 및 DB 쿼리 시 명시적인 정렬 기준(`ORDER BY`) 미설정. 시나리오 파일의 단순 쉼표(,) 누락으로 인한 워커 데드락 위험.

---

## 2. 해결 전략 및 실제 코드 적용

### ① 상태 기반 동기화 (State-Driven Sync)
"답변 완료 후 질문 생성"이라는 논리적 순서를 보장하기 위해, 코드 레벨이 아닌 **DB Commit** 상태를 기준으로 태스크를 발행합니다.

```python
# [위치] backend-core/routes/transcripts.py (Line 79-96)

# 1. 지원자 답변을 DB에 먼저 저장
db.add(transcript)
db.commit()      # [핵심] DB 저장이 물리적으로 완전히 끝난 것을 확정(Commit)
db.refresh(transcript)

# 2. DB 저장이 성공적으로 끝난 '상태'에서만 다음 질문 생성 요청
if str(transcript.speaker).lower() in ("user", "speaker.user"):
    celery_app.send_task(
        "tasks.question_generation.generate_next_question",
        args=[transcript.interview_id],
        queue="gpu_queue"
    )
```

#### 💡 [상세 해설] commit()의 진짜 역할 (진행 vs 정상 진행의 차이)
1. **"진행"은 되지만 "대화"가 안 됩니다 (심각한 인지부조화)**
commit()을 안 하고 다음 질문 생성(send_task)을 하면, 서비스는 돌아가지만 AI 면접관은 **'방금 지원자가 한 말을 못 들은 상태'**로 다음 질문을 던지게 됩니다.

- **정상 흐름:** 지원자: "저는 소통을 잘합니다" -> commit -> AI: "오, 소통 능력 중 구체적인 사례는요?" (정상 진행)
- **commit 누락 시:** 지원자: "저는 소통을 잘합니다" -> (AI는 이 정보를 모름) -> AI: "지원자님, 왜 아직 아무 말씀도 안 하시나요?" 또는 "자기소개 부탁드립니다" (면접은 진행되지만 대화가 파괴됨)
- **결론:** commit()이 없으면 면접이 **"진행"**은 되나, 지원자 입장에서는 **"내 말을 씹고 딴소리하는 AI"**를 만나게 되어 면접 경험이 완전히 망가집니다.

2. **"조기 생성"이 진짜 무서운 이유 (Race Condition)**
사용자님이 말씀하신 "조기 생성"은 단순히 시간이 빨라지는 문제가 아니라 **"데이터가 도착하기 전의 빈 공간"**을 AI가 낚아채는 게 문제입니다.

- **commit 전:** 데이터베이스 입장에서는 아직 이 답변이 존재하지 않는 상태입니다.
- **조기 생성 발생:** 이 찰나에 AI 워커가 "자, 다음 질문 만들자!" 하고 DB를 뒤지면? 데이터가 0건입니다.
- **결과:** AI는 지원자가 답변을 아예 안 했다고 판단하고 "답변을 안 하셨는데, 다음으로 넘어갈까요?" 같은 아주 어색한 질문을 뱉어버립니다.

3. **"마치기도 전에"의 진짜 의미**
여기서 "마치다"는 사용자가 말을 멈추는 것뿐만 아니라, **"시스템이 그 말을 기록으로 확정(Commit) 짓는 것"**까지를 포함합니다.

- **commit이 없으면:** 시스템 입장에서는 사용자가 아직 말을 안 마친(기록 안 된) 상태입니다.
- **그런데 질문부터 나오면?** 지원자는 "어? 나 아직 말 다 안 했는데?(또는 이제 막 했는데?)"라고 느끼게 되는 것이죠.

### ② 쿼리 정렬 강제화 (Order Enforcement)
DB에서 데이터를 가져올 때 순서가 무작위로 섞이지 않도록 모든 조회 쿼리에 정렬 기준을 명시했습니다.

#### 📖 [상세 해설] 비유: "페이지 번호 없는 일기장"
말씀하신 **'쿼리 정렬 강제화(Order Enforcement)'**가 왜 필수적인지, 그리고 이게 왜 면접 리포트의 신뢰성과 직결되는지 '일기장' 비유를 통해 아주 자세하게 설명해 드릴게요.

데이터베이스(DB)는 거대한 일기장과 같습니다. 우리가 면접 내용을 기록할 때, 순서대로 적긴 하지만 DB라는 일기장은 조금 특이한 성질이 있습니다.

- **DB의 내부 동작:** 일기장에 내용을 적다 보면 공간이 부족해서 뒷장에 적기도 하고, 중간 내용을 수정하면 그 내용을 다른 빈 곳으로 옮겨 적기도 합니다. (PostgreSQL의 MVCC라는 물리적 저장 방식 때문입니다.)
- **ORDER BY가 없을 때:** 만약 일기장에 **'페이지 번호'**가 없다면, 나중에 일기장을 펼쳤을 때 DB는 그냥 **자기 손에 잡히는 페이지(물리적으로 가까운 데이터)**부터 아무렇게나 보여줍니다.
- **현상:** 어제 쓴 일기 뒤에 오늘 쓴 일기가 나오는 게 아니라, 갑자기 1시간 전에 쓴 내용이 맨 앞에 나오고, 아침에 한 질문이 맨 뒤에 나오는 **'뒤죽박죽 일기장'**이 됩니다.

#### 😱 왜 이게 면접 시스템에서 치명적인가요?
단순히 순서가 바뀌는 게 아니라, 서비스의 **'논리와 신뢰'**가 완전히 깨지기 때문입니다.

- **리포트의 붕괴:** 사용자가 면접을 마치고 리포트를 보는데, [질문 1]에 대한 답변이 [질문 5] 옆에 붙어 있고, 면접 끝에 나온 꼬리 질문이 맨 처음에 나옵니다. 사용자는 **"이 시스템 고장 났네?"**라고 생각하게 됩니다.
- **프론트엔드 오류:** 화면에서 이전 대화 목록을 보여줘야 하는데, 순서가 계속 바뀌면 화면이 깜빡거리거나 대화 흐름이 엉망이 됩니다.
- **AI의 혼란:** AI도 과거 대화를 불러올 때 순서가 뒤섞이면 맥락을 파악하지 못하고 **"방금 하신 말씀(사실은 10분 전 대화)"**이라며 엉뚱한 반응을 보입니다.

#### 🛠️ 코드로 해결한 '타임라인 100% 보장' 전략
우리는 이 문제를 해결하기 위해 모든 조회 쿼리에 **'강력한 페이지 번호(정렬 기준)'**를 부여했습니다.

1. **AI 질문 조회 (order_by(Transcript.id))**
질문은 생성된 순서(ID)가 곧 면접의 진행 순서입니다.
```python
# 가장 확실한 기준인 'ID(생성 순서)'를 기준으로 줄을 세웁니다.
.order_by(Transcript.id)
```
**효과:** 사용자는 항상 실시간으로 생성된 **'다음 질문'**을 정확한 순서대로 받을 수 있습니다.

2. **전체 대화 기록 조회 (order_by(Transcript.timestamp))**
면접 리포트는 **'시간의 흐름'**이 가장 중요합니다.
```python
# 0.001초 단위의 타임스탬프를 기준으로 줄을 세웁니다.
.order_by(Transcript.timestamp)
```
**효과:** 면접이 끝난 후 생성되는 리포트에서 단 하나의 오차도 없이 질문-답변의 타임라인을 완벽하게 복원합니다.

## 🎯 최종 요약 및 발표용 핵심 멘트

### [커밋 및 동기화 요약]
사용자님 말씀처럼 commit()이 없어도 서비스는 "굴러는 갑니다." 하지만 commit()을 확실히 해줌으로써 얻는 진짜 이득은 **"흐름의 동기화"**입니다.
- **데이터의 확정:** "지원자의 답변이 이제 공식 기록이 되었다!"라는 선언
- **AI의 인지:** "AI야, 방금 확정된 이 기록을 보고 다음 질문을 만들어라!"라는 정확한 가이드
- **즉, commit()은 '면접의 진행'을 위한 버튼이 아니라, '면접의 품질과 논리를 지키기 위한 '마침표'인 것입니다.**

### [정렬 및 정합성 요약]
"저희는 비동기 환경에서 데이터가 물리적으로 저장되는 순서가 보장되지 않는다는 점에 주목했습니다. 이를 해결하기 위해 모든 DB 조회 로직에 **ID와 타임스탬프 기반의 명시적 정렬(Order By)**을 강제했습니다. 이 한 줄의 코드가 단순히 순서를 맞추는 것을 넘어, 면접 데이터의 정합성과 사용자 리포트의 신뢰성을 100% 보장하는 핵심 장치가 되었습니다."
