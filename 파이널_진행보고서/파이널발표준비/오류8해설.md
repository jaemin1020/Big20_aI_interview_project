# [오류 사례 8] RAG 및 벡터 DB 연동 최적화 해설

이 문서는 프로젝트 수행 중 발생한 **RAG(검색 증강 생성) 파이프라인의 검색 실패**와 **DB 세션 누수** 문제를 해결한 과정을 기술적 비유와 코드를 통해 상세히 설명합니다.

---

## 1. 문제 상황 (Problem Definition)
*   **현상:** 이력서 기반의 개인화 질문이 생성되지 않고 일반적인 질문만 반복됨. DB에는 데이터가 존재하나 검색 결과가 빈 배열(`[]`)로 반환됨.
*   **원인:** 필터링 필드명 불일치(`chunk_type` vs `category`) 및 DB 연결 파라미터 누락으로 인한 세션 누수.

---

## 2. 기술적 해결 비유: "건물을 드나드는 문"

벡터 DB와 연결하는 방식을 건물을 드나드는 과정에 비유하면 다음과 같습니다.

### 🟢 원래 방식 (문제 발생의 근본 원인)
> AI(PGVector)가 DB 건물을 드나들 때마다 자기 전용 **"개구멍(새로운 커넥션)"**을 새로 파고 들어가는 방식입니다.

*   **왜 새로 만들면 안 되나요?**: DB가 수용 가능한 통로(Connection) 개수는 한정되어 있습니다. 비동기 워커들이 각자 통로를 뚫고 나갈 때 닫지 않으면(**누수**), 순식간에 DB의 한계치를 초과하여 서비스 전체가 중단됩니다.
*   **문제 상황 1 (세션 누수):** AI가 나올 때 구멍을 메우지 않고 그냥 가버리면 건물이 구멍투성이가 되어 무너집니다. (**DB 연결 제한 초과로 인한 다운**)
*   **문제 상황 2 (트랜잭션 충돌):** 공식 안내원(Engine) 없이 각자 구멍으로 들어오니, 누가 데이터를 고치고 있는지 읽고 있는지 서로 몰라 충돌이 납니다. (**비정상적인 트랜잭션 경고**)
*   **문제 상황 3 (표지판 불일치):** 건물에 들어와서 사물함을 찾을 때, 사물함은 `chunk_type`인데 AI는 `category`라는 쪽지를 들고 찾고 있는 셈입니다. (**분명 데이터가 있는데 못 찾아서 빈 배열 반환**)

### 🔵 개선된 방식 (프로젝트 적용: `connection=engine`)
> 우리가 이미 튼튼하게 만들어 놓은 공식 **"정문(Engine)"**과 거기서 보관하는 **"마스터키"** 하나를 AI에게 빌려준 것입니다.
*   **해결:** AI는 이제 힘들게 구멍을 팔 필요가 없습니다. 우리가 준 마스터키로 정문을 열고 들어가 할 일을 합니다.
*   **결과:** AI가 일을 마치고 정문을 나가면, 시스템(SQLAlchemy)이 알아서 문을 잠가줍니다. (**누수 원천 차단**)
*   **질서:** 모든 AI가 정문을 통해 들어오므로 안내원(Engine)이 번호표를 줍니다. 싸울 일이 없고 줄 서서 질서 있게 데이터를 가져갑니다. (**안정적인 트랜잭션**)

---

## 3. [심화] 왜 DB 연결을 반드시 '닫아야(Close)' 하나요?

"그냥 주소 찍고 들어가서 데이터만 가져오면 되지 않나?"라는 의문에 대한 **'전화 통화'** 비유입니다.

### 📞 DB 연결은 "전화 통화"와 같습니다
데이터만 가져오고 끝나는 게 아니라, 데이터를 가져오기 위해 **선(Line)을 하나 차지하고 있는 상태**가 됩니다.

1.  **전화를 건다 (Connect):** DB 주소를 넣고 연결합니다.
2.  **용건을 말한다 (Query):** "이력서 데이터 좀 줘!"
3.  **대답을 듣는다 (Response):** "여기 있어!"
4.  **전화를 끊는다 (Close / Disconnect):** **← 이 부분이 "닫기"입니다.**

### 😱 만약 전화를 안 끊는다면? (누수 발생)
용건이 끝났는데 수화기를 내려놓지 않고 그냥 책상 위에 올려둔 채로 딴 일을 하러 가는 것과 같습니다.

*   **DB 입장:** "어? 아직 저 손님이 전화를 안 끊었네? 뭔가 더 물어볼 게 있나 보군. **전화기 한 대(Connection)를 계속 비워두고 기다려야지.**"
*   **문제 발생:** 다른 손님들이 전화를 거는데, DB의 전화기 100대가 전부 '수화기가 내려지지 않은 상태'로 꽉 차 버립니다.
*   **결과:** 새로 전화를 거는 사람들은 **"통화 중(Busy)"** 표시만 뜨고 아무도 DB에 접근할 수 없게 됩니다. 이게 바로 **서버 다운**입니다.

## 3. 실제 코드 적용 분석

### ① 필드명 통일 (데이터 일관성 확보)
저장할 때와 검색할 때의 키워드를 `chunk_type`으로 대통일했습니다.

```python
# [저장] ai-worker/tasks/pgvector_store.py (Line 69)
m["chunk_type"] = item.get("type", "unknown") # 'chunk_type'이라는 이름으로 견출지 부착

# [검색] ai-worker/tasks/rag_retrieval.py (Line 94)
search_filter["chunk_type"] = filter_type # 'chunk_type'이라는 이름으로만 검색
```

### ② 통로 공유 설계 (`connection=engine`)
별도의 연결을 만들지 않고 기존에 검증된 통로(engine)를 공유하도록 설정했습니다.

```python
# [연결] ai-worker/tasks/rag_retrieval.py (Line 57-62)
_vector_stores[collection_name] = PGVector(
    connection_url,        # 공식 DB 주소 전달
    embedder,              # 임베딩 모델 전달
    collection_name=collection_name,
    connection=engine      # [중요] 우리가 만든 '정문(engine)' 객체를 직접 주입!
)
```

### ③ 명시적 세션 관리 (자원 회수)
`with` 문을 사용하여 작업이 끝나면 즉시 세션이 반환되도록 했습니다.

```python
# [관리] ai-worker/tasks/resume_embedding.py (Line 59)
with Session(engine) as session: # 세션을 명시적으로 열고
    # ... 작업 수행 ...
    session.commit() # 트랜잭션을 닫으면 시스템이 알아서 정문을 잠금!
```

## 🎯 최종 요약 (발표용)

1.  **누수 차단:** AI가 DB에 들어갈 때마다 새로운 통로를 만드는 대신, 우리가 관리하는 **정문(Engine)을 같이 쓰게** 해서 통로가 무한정 늘어나는 것을 막았습니다.
2.  **공유 경제:** 비싼 DB 연결 자원을 AI가 독차지하지 않고 **나눠 쓰게 설계**해서 전체 시스템 성능을 높였습니다.
3.  **안정성:** 관리가 안 되는 '개구멍'을 없애고 공식적인 **통로(Engine)로만 질서 있게 오가게** 만든 것입니다.

> **"즉, AI가 DB를 망가뜨리지 않고 아주 깔끔하게 필요한 정보만 가져가도록 '통로 관리'를 철저히 한 고성능 시스템입니다."**
